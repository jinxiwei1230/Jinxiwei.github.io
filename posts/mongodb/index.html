(一) 文档数据库概述

1. 文档数据库核心特点

  1. 灵活的数据模型：
    • 文档是基本存储单位，采用JSON/BSON格式
    • 支持嵌套结构和树形数据存储
    • 文档结构可自描述，无需严格模式定义
  2. 强大的功能支持：
    • 支持多种索引类型（单字段、复合、全文、地理空间等）
    • 提供丰富的查询语言和聚合框架
    • 支持ACID事务管理机制
  3. 扩展性与高可用：
    • 分布式集群架构（分片+复制集）
    • 易于水平扩展，支持高并发访问
    • 自动故障转移，保障数据高可用性
  4. 完善的生态系统：
    • 支持多种编程语言驱动
    • 提供管理监控工具（如MongoDB Atlas、Compass）
    • 具备完善的安全机制（认证、加密、审计）

2. 文档数据模型优势

  • 自包含性：文档同时包含数据及其结构信息
  • 灵活性：同一集合中的文档可具有不同结构
  • 高效性：相关数据存储在单一文档中，减少join操作

3. XML与JSON比较

特性 XML JSON
格式 标记语言，语法严格 轻量级键值对结构
扩展性 通过DTD/XSD定义模式 无严格模式定义
可读性 相对冗长 简洁易读
处理效率 解析复杂 解析高效
数据类型支持 有限 基本类型+嵌套
典型应用场景 企业级数据交换、文档标记 Web API、NoSQL数据库存储

4. JSON与BSON深入对比

JSON特点：

  • 人类可读的文本格式
  • 基本结构：对象（无序键值对）和数组（有序值列表）
  • 支持数据类型：字符串、数字、布尔值、null、对象、数组

BSON增强特性：

  1. 二进制编码：
    • 存储空间更紧凑
    • 包含长度前缀，支持快速跳转
    • 例：{"hello": "world"} → \x16\x00\x00\x00\x02hello\x00\x06\x00\x00\x00world\x00\x00
  2. 扩展数据类型：
    • 日期（Date）
    • 二进制数据（BinData）
    • 对象ID（ObjectId）
    • 正则表达式
    • JavaScript代码
    • 时间戳（Timestamp）
    • 小数128（Decimal128）
  3. 每种类型都有一个数字代号和一个英文别称
    • $type 运算可以返回field的类型
    • $isNumber运算可以返回是否是数值类型
  4. 查询优势：
    • 支持类型操作符：$type, $isNumber 示例查询：db.collection.find({"field": {$type: "date"}})

(二) MongoDB数据存储模型逻辑架构

1. 关键概念

MongoDB数据存储模型中的核心概念包括：

  • 文档（Document）
  • 集合（Collection）
  • 数据库（Database）

它们与关系型数据库MySQL的对应关系如下：

MongoDB MySQL
_id 主键（Primary Key)
字段（Field） 列（Column）
文档（Document） 行（Row）
集合（Collection） 表（Table）
数据库（Database） 数据库（Database）

2. 数据库（Databases）

  • 在将文档加入集合之前，MongoDB需要将集合加到数据库中。
  • 一个MongoDB主机上通常会有多个数据库。
  • 数据库名称需使用UTF-8字符，长度不能超过64个字符，且不得包含空格、'.'、'$'、'/'、'\\'、'\0'等特殊字符。
  • MongoDB默认创建以下4个数据库：
    • admin：根级数据库，供系统管理员使用。
    • local：不会被复制，仅限本地服务器访问。
    • config：用于存储分片集群的配置信息。
    • test：默认连接的数据库。

3. 集合（Collection）

  • 集合相当于一个没有固定模式的表。
  • 一个集合由多个文档组成，集合中的文档结构可以不同。
  • 集合名称由UTF-8字符组成。
  • 不能以system.作为集合名称前缀，例如system.users存储用户信息。
  • 不能使用"$"作为保留字。

4. 文档（Document）

  • 每个文档都有唯一的_id字段，类似于主键。
  • 文档结构可变，键/值对是有序的。
  • 命名规范：
    • 区分大小写
    • 不能包含'\0'
    • 避免使用'.'和'$'

5. ObjectId 机制

MongoDB 使用 ObjectId 作为默认主键，具有以下特点：

  • 由 new ObjectId() 生成，占用 12 个字节。
  • 每个文档标识中包含标识产生时间、机器标识、进程和自增序列四方面内容，组合起来保障唯一性。
  • 组成结构：
    1. 时间戳（4字节）：按创建时间排序。
    2. 机器标识（3字节）：不同机器生成不同 ObjectId。
    3. 进程标识（2字节）：确保同一台机器上的多个进程生成唯一ID。
    4. 计数器（3字节）：在同一秒内提供 16,777,216 个不同的 ObjectId。
  • 也可以使用整数或其他类型作为 _id。
  • 使用 ObjectId 可以确保唯一性，无需手动管理。

(三) MongoDB 数据存储与文档模型设计

3.1 设计原则

  • 抽象关键业务实体：
    • 业务需求决定 MongoDB 中的集合，如：
      • 客户集合（customers）
      • 产品集合（products）
      • 订单集合（orders）
      • 供应商集合（suppliers）
  • 文档字段设计：
    • 经常一起访问的字段 应该存储在同一个文档中，提高查询效率。
    • 较少访问的字段 可拆分为子文档或存储在其他集合中。

3.2 文档关系建模

MongoDB 提供两种常见的文档建模方式：

  1. 内嵌文档（嵌套）：

    • 适用于一对一或一对多且数据紧密相关的情况。

    • 适合需要一起读取的字段，减少查询次数。

    • 示例（嵌套地址信息）：

      {
  "_id": "joe",
  "name": "Joe Bookreader",
  "address": {
    "street": "123 Fake Street",
    "city": "Faketon",
    "state": "MA",
    "zip": "12345"
  }
}

  2. 引用关系（外键方式）：

    • 适用于一对多或多对多且数据独立性较高的情况。

    • 适合需要独立查询的实体，避免数据冗余。

      // patron（用户）集合
{
  "_id": "joe",
  "name": "Joe Bookreader"
}

// address（地址）集合
{
  "patron_id": "joe",
  "street": "123 Fake Street",
  "city": "Faketon",
  "state": "MA",
  "zip": "12345"
}

3.3 大文档分解

1、思路 1：按访问频率分解

  • 经常访问的字段：存入主文档。

  • 不经常访问的字段：拆分为子集合。

电影数据拆分示例

  • movie collection（主要存储高频访问字段）

    {
  "_id": 1,
  "title": "The Arrival of a Train",
  "year": 1896,
  "runtime": 1,
  "released": ISODate("1896-01-25"),
  "type": "movie",
  "directors": ["Auguste Lumière", "Louis Lumière"],
  "countries": ["France"],
  "genres": ["Documentary", "Short"]
}

  • movie_details collection（存储低频访问字段，如海报、剧情、评分等）

    {
  "_id": 156,
  "movie_id": 1,  // 关联 movie collection
  "poster": "http://example.com/movie.jpg",
  "plot": "A group of people are waiting for a train...",
  "fullplot": "Detailed movie description...",
  "imdb": { "rating": 7.3, "votes": 5043, "id": 12 },
  "tomatoes": { "viewer": { "rating": 3.7, "numReviews": 59 },
  "lastUpdated": ISODate("2024-01-29T00:02:53") }
}

  • 减少查询时的数据传输量，提升查询效率

  • 优化存储，避免每次查询都加载完整数据

  • 支持索引优化，提高查询性能

  • 产品评价数据拆分

  • 方式1：最近 Top-K 评论嵌套存储 适用于希望在查询产品详情时同时获取最新评论的情况：

{
  "_id": 1,
  "name": "Super Widget",
  "description": "This is the most useful item in your toolbox.",
  "price": { "value": NumberDecimal("119.99"), "currency": "USD" },
  "reviews": [
    {
      "review_id": 786,
      "review_author": "Kristina",
      "review_text": "This is indeed an amazing widget.",
      "published_date": ISODate("2019-02-18")
    },
    {
      "review_id": 785,
      "review_author": "Trina",
      "review_text": "Nice product. Slow shipping.",
      "published_date": ISODate("2019-02-17")
    }
  ]
}

方式2：将所有评论存储在单独的 review collection 适用于评论数据量较大的情况：

{
  "review_id": 786,
  "product_id": 1,
  "review_author": "Kristina",
  "review_text": "This is indeed an amazing widget.",
  "published_date": ISODate("2019-02-18")
}
  • 避免单个文档过大，影响查询性能
  • 灵活查询评论数据，支持分页加载
  • 便于扩展，可以增加评论分析功能

（四）MongoDB 文档数据之间的引用关系

1、文档引用

在 MongoDB 中，可以通过 引用方式 关联多个文档，以减少数据冗余，提高查询效率。

方法 1：在 publisher 文档中引用 book 文档

{
  "name": "O'Reilly Media",
  "founded": 1980,
  "location": "CA",
  "books": [123456789, 234567890]
}
{
  "_id": 123456789,
  "title": "MongoDB: The Definitive Guide",
  "author": ["Kristina Chodorow", "Mike Dirolf"],
  "published_date": ISODate("2010-09-24"),
  "pages": 216,
  "language": "English"
}

优点：可以方便查询某个出版社的所有书籍 缺点：如果书籍数量过多，数组 books 可能会变得很长，影响性能。

方法 2：在 book 文档中引用 publisher 文档

{
  "_id": "oreilly",
  "name": "O'Reilly Media",
  "founded": 1980,
  "location": "CA"
}
{
  "_id": 123456789,
  "title": "MongoDB: The Definitive Guide",
  "author": ["Kristina Chodorow", "Mike Dirolf"],
  "published_date": ISODate("2010-09-24"),
  "pages": 216,
  "language": "English",
  "publisher_id": "oreilly"
}

优点：避免了 publisher 文档中 books 数组无限增长的问题。 缺点：查询某个出版社的所有书籍时，需要 publisher_id 进行 关联查询（可以使用 $lookup）。

2、$lookup 关联查询

MongoDB 3.2+ 版本后支持 $lookup 操作，可以在查询时将不同集合的数据进行关联。

{
  "$lookup": {
    "from": "publishers",
    "localField": "publisher_id",
    "foreignField": "_id",
    "as": "publisher_info"
  }
}

作用：相当于 SQL 里的 JOIN，可以在查询 book 文档时自动获取 publisher 的详细信息。

3、 使用 DBRef 进行跨库引用

DBRef 提供了 类似外键 的引用方式，但相比 _id 直接引用，DBRef 更加通用，可用于跨数据库的文档关联。

// 在dep集合中插入一个部门文档
{
  "name": "CS",
  "num": 15,
  "people": [
    { "$ref": "people", "$id": ObjectId("5d81dd075abbb6081b3e1efa"), "$db": "myTest" },
    { "$ref": "people", "$id": ObjectId("5d81dd315abbb6081b3e1efb"), "$db": "myTest" }
  ]
}
> db.dep.insertOne({
    name: "CS", 
    num: 15,
    people: [
        DBRef("people", ObjectId("5d81dd075abbb6081b3e1efa"), "myTest"),
        DBRef("people", ObjectId("5d81dd315abbb6081b3e1efb"), "myTest"),
        DBRef("people", ObjectId("5d81df1d5abbb6081b3e1efd"), "myTest")
    ]
})

优点：可以跨数据库引用数据。 缺点：查询时需要 额外的解引用（fetch） 操作，性能比 $lookup 低。

4、MongoDB 时序数据存储优化

1. 传统存储方式

假设有一个 temperatures 集合，每个文档存储单个时间点的温度：

{
  "_id": 1,
  "sensor_id": 12345,
  "timestamp": ISODate("2025-01-31T10:00:00.000Z"),
  "temperature": 40
}

问题：当数据量很大时，单个点查询效率低，批量查询变得昂贵。

2. 分桶（Bucket Pattern）优化

使用分桶模式，每个文档存储一个时间段的数据：

{
  "_id": 1,
  "sensor_id": 12345,
  "start_date": ISODate("2025-01-31T10:00:00.000Z"),
  "end_date": ISODate("2025-01-31T10:59:59.000Z"),
  "measurements": [
    { "timestamp": ISODate("2025-01-31T10:00:00.000Z"), "temperature": 23 },
    { "timestamp": ISODate("2025-01-31T10:01:00.000Z"), "temperature": 26 },
    { "timestamp": ISODate("2025-01-31T10:32:00.000Z"), "temperature": 22 }
  ],
  "transaction_count": 32,
  "sum_temperature": 883
}

优点：

  • 适合批量查询，可以快速计算统计值（如平均温度）。
  • 查询特定时间段的数据更快，减少了查询文档的数量。
方法 适用场景 优势 劣势
文档引用（方法 1） 适用于一对多的关系，如出版社-书籍 便于查询所有相关子文档 数组字段可能变长，影响性能
文档引用（方法 2） 适用于一对多的关系，如书籍-出版社 解决数组字段变长问题 查询时需要 $lookup
DBRef 适用于跨库关联 可实现跨数据库关联 需要额外 fetch() 操作，查询较慢
时序数据存储（普通模式） 适用于传感器等高频数据 结构清晰 查询大批量数据时较慢
时序数据存储（分桶模式） 适用于大规模时序数据 提高批量查询效率，减少存储占用 需要额外的批量更新逻辑

（五）MongoDB数据存储引擎类型

1. WiredTiger（默认存储引擎）

  • 特点：
    • 支持 文档级别的并发控制，提高多线程并发性能
    • 数据持久化存储，保证数据可靠性
    • 支持数据压缩（减少存储空间）
    • 提供事务支持（多文档事务，从 MongoDB 4.0 开始支持）
    • 支持加密（企业版功能）
  • 适用场景：
    • 需要高并发读写的应用，如电商、社交平台
    • 需要高效存储和数据压缩的系统

2. In-Memory 存储引擎

  • 版本支持：MongoDB 企业版
  • 特点：
    • 数据仅存储在内存中，不写入磁盘（极低延迟）
    • 重启后数据丢失
    • 适用于高吞吐量应用
  • 适用场景：
    • 需要极低延迟的应用，如 实时分析、缓存
    • 临时数据处理，如中间计算数据存储

3. MMAPv1（早期存储引擎）

  • 特点：
    • 采用 内存映射文件（Memory-Mapped Files） 存储数据
    • 基于页级锁（Page-Level Locking），并发性能较低
    • 不支持事务
  • 适用场景：
    • 仅用于 MongoDB 旧版本迁移
    • 低并发的应用

存储引擎选择建议

存储引擎 适用场景 主要优势
WiredTiger 读写并发高，数据持久化 高并发、数据压缩、事务支持
In-Memory 低延迟、高速读写 内存存储，适合缓存/实时分析
MMAPv1（已淘汰） 旧版本兼容 适用于低并发应用

多存储引擎并存

MongoDB 允许在同一实例中使用不同存储引擎，例如：

  • WiredTiger + In-Memory：持久化存储 + 高速缓存
  • WiredTiger + 第三方存储引擎（如 RocksDB）：灵活适应不同负载需求

结论：

  • 新项目推荐使用 WiredTiger
  • 高性能应用可以选择 In-Memory
  • 旧版本迁移时可以考虑 MMAPv1，但需升级

(六)MongoDB 基础操作

1. 数据库操作

1.1 创建与切换数据库

  • MongoDB 没有 显式的数据库创建命令，而是通过使用数据库名的方式创建：

    use myTest  # 切换到 myTest 数据库（如果不存在，将在插入数据时自动创建）

  • 创建集合（显式创建数据库）：

    db.createCollection('user')  # 创建 user 集合，此时 myTest 数据库才真正创建

  • 查看数据库：

    show dbs  # 查询所有数据库（空数据库不会显示）
db.getName()  # 获取当前数据库名称

  • 删除数据库：

    db.dropDatabase();  # 删除当前数据库

2. 数据库管理常用命令

命令 功能
show dbs 显示所有数据库（仅包含数据的数据库）
show users 显示当前数据库的所有用户
show collections 显示当前数据库的所有集合
db.help() 显示数据库操作的帮助信息
db.stats() 显示数据库状态（集合数、空间占用情况等）
db.version() 显示 MongoDB 版本
db.getMongo() 查看数据库连接的服务器地址
db.createUser(userDocument) 创建用户
db.auth(username, password) 进行数据库认证
db.dropUser(username) 删除用户

3. 集合操作

3.1 集合管理

  • 创建集合（可选参数设定集合属性）：

    db.createCollection("log", { capped: true, size: 6142800, max: 10000 })
    • capped: true：固定大小集合
    • size：集合最大存储大小（字节）
    • max：集合最多存储的文档数（FIFO 机制）

  • 查询集合：

    db.getCollectionNames();  # 获取当前数据库所有集合名称
db.getCollection("user");  # 获取 user 集合
db.printCollectionStats();  # 获取集合统计信息

  • 删除集合：

    db.user.drop();  # 删除 user 集合

4. 文档（数据）操作

4.1 插入数据

db.user.insert({name: "Alice", age: 25, city: "Beijing"})  # 插入单个文档
db.user.insertMany([{name: "Bob"}, {name: "Charlie"}])  # 插入多个文档
db.user.insertOne({name: "David"})  # 插入一个文档

4.2 查询数据

db.user.find()  # 查询所有文档
db.user.find().pretty()  # 美化显示查询结果
db.user.find({name: "Alice"})  # 查询 name 为 Alice 的文档
db.user.findOne()  # 查询一条文档
db.user.count()  # 统计集合中文档数量

4.3 更新数据

db.user.update({name: "Alice"}, {$set: {age: 26}})  # 更新 Alice 的年龄
db.user.updateOne({name: "Bob"}, {$set: {city: "Shanghai"}})  # 仅更新一条
db.user.updateMany({}, {$set: {status: "active"}})  # 批量更新所有文档
db.user.replaceOne({name: "Charlie"}, {name: "Charlie", age: 30})  # 替换 Charlie 文档

4.4 删除数据

db.user.deleteOne({name: "Alice"})  # 删除一个文档
db.user.deleteMany({status: "inactive"})  # 删除多个文档
db.user.remove({city: "Beijing"}, false)  # 仅删除第一个匹配项
db.user.drop()  # 删除 user 集合（所有数据）

MongoDB集群架构要点

核心组件

  1. 分片(Sharding)：

    • 水平分割数据到多个分片
    • 通过分片键(shard key)路由请求
    • 支持自动平衡数据分布

  2. 复制集(Replica Set)：

    • 每个分片由一组复制集构成
    • 包含1个主节点(Primary)和多个从节点(Secondary)
    • 自动故障转移（通常60秒内完成）

  3. 配置服务器(Config Server)：

    • 存储集群元数据和分片信息
    • 采用特殊复制集架构

  4. 查询路由器(Mongos)：

    • 应用程序的访问入口
    • 聚合来自各分片的结果

典型生产部署架构

应用程序 → Mongos路由层
            ↓
    配置服务器集群(3节点)
            ↓
   分片1(3节点复制集)
   分片2(3节点复制集)
   ...
   分片N(3节点复制集)

这种架构同时保证了数据的可扩展性（通过分片）和高可用性（通过复制集），能够支持PB级数据管理和每秒数百万次操作。
