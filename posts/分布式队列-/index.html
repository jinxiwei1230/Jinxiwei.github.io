第二章 分布式消息队列

Kafka

Kafka 概述

0、数据会越来越多，此时可能需要增加多条数据线，每条数据线将收集到的数据导入不同的存储和分析系统。若仍采用之前的数据收集模式，会有以下潜在问题：

  • 数据生产者和消费者耦合度过高
  • 生产者和消费者间数据处理速率不对等
  • 大量并发的网络连接对后端消费者不够友好

1、引入 Kafka 作为中间件在分布式数据系统中的重要作用：

  • 消息中间件：

    • 作用：Kafka 作为消息中间件，介于数据生产者（如 Web Server）和数据消费者（如 Hadoop 集群、实时监控系统）之间。
    • 好处：通过引入 Kafka 消息中间件，生产者和消费者之间无需直接通信，因此减少了两者之间的依赖性。即使生产者或消费者发生变化，对方也不会受到影响，这提升了系统的可扩展性和灵活性。

  • 消息队列：

    • 作用：Kafka 的消息队列功能可以缓存数据，使得消费者能够按需读取和处理数据。
    • 好处：Kafka 中缓存的数据可以重复消费，这非常适合需要重新处理历史数据的场景。比如，如果最初的处理结果有误，消费者可以重复读取这些数据进行修正。此外，消息队列还能平衡生产者的数据生成速度和消费者的数据处理速度，缓解生产者快、消费者慢的压力。

  • 发布-订阅系统：

    • 作用：Kafka 可以充当发布-订阅系统，消费者可以根据感兴趣的主题进行订阅。
    • 好处：生产者一旦产生某个主题的数据，所有订阅该主题的消费者都会快速接收到新数据，实现了实时数据推送。同时，Kafka 的设计允许随时增加新的消费者，无需更改系统配置，这极大提高了系统的灵活性和扩展性。

  • 消息总线：

    • 作用：Kafka 作为消息总线，接收所有生产者发送的数据，然后分流到各个消费者。

2、Kafka 特点： 高吞吐量、良好的扩展性、持久性和可靠性

3、Kafka 和 Flume 都是数据传输系统，但在架构、应用场景和集成方面各有不同，具体如下： Kafka

  1. 发布-订阅模型：

    • Kafka 基于发布-订阅模型，主要由 生产者、主题 和 消费者 组成。
    • 用途：Kafka 非常适合用于实时数据的发布和订阅，支持高吞吐量的大数据实时处理。

  2. 实时消息传递：

    • Kafka 的设计更侧重于实时消息的传递，能够确保数据从生产者到消费者的低延迟。
    • 应用场景：适合实时数据分析、监控和流式处理场景。

  3. 丰富的 API 和流处理集成：

    • Kafka 提供多种 API，可以与流处理框架（如 Spark Streaming、Flink）和其他系统（如 Storm、Hadoop）无缝集成，尤其适合构建实时数据管道。

Flume

  1. 数据流模型：

    • Flume 基于数据流模型，架构上有 source（源）、channel（通道）和 sink（汇）三大组件，数据流从 source 经 channel 传递至 sink。
    • 用途：Flume 特别适用于日志收集与传输，常用于将大量分布式日志数据高效传送到集中系统。

  2. Hadoop 集成优化：

    • Flume 专门为日志数据到 Hadoop 生态系统的传输进行了优化，与 HDFS 和 HBase 集成效果好。
    • 应用场景：适合批量数据传输、日志数据存储和离线数据传输等场景。

Kafka 设计架构

Kafka 的基本架构
  1. Producer（生产者）：
  • 生产者负责将数据发送到 Kafka 集群中的 Broker。它将数据写入指定的 Topic。
  1. Broker（代理）：
  • Broker 是 Kafka 的核心组件，负责接收、存储和转发数据。多个 Broker 组成一个 Kafka 集群，形成一个可靠的分布式消息存储系统。
  • 每个 Broker 负责一个或多个 Topic 的数据，并将每个 Topic 的数据分为多个分区（Partition），以实现负载均衡和数据的并行处理。
  1. Consumer（消费者）：
  • 消费者从 Broker 中读取数据进行处理。它可以订阅一个或多个 Topic，并按照自身需求处理数据。
  1. ZooKeeper：
  • ZooKeeper 用于协调和管理 Kafka 集群，负责 Broker 的注册、配置管理、服务发现等功能。它提供了集群的元数据存储。
数据存储和分区
  • Topic 和 Partition：
    • 在 Kafka 中，数据按照主题（Topic）进行组织。同一 Topic 的数据根据策略分为多个 Partition，这样可以实现数据的并行处理和负载均衡。
    • 每个 Partition 中的消息是有序的，并且可以设置多个副本以提高数据的可靠性，防止数据丢失。
Push-Pull 架构

  • Push（生产者）：

    • 生产者将数据直接推送（push）到 Broker。生产者可以选择向特定的 Partition 发送数据，这样可以根据需求进行负载分配。

  • Pull（消费者）：

    • 消费者从 Broker 拉取（pull）数据。这种方式使消费者可以根据自己的实际负载和需求来获取数据，避免了生产者将数据强制推送给消费者，导致消费者过载的情况。
优势

  1. 灵活的负载管理：

    • 消费者根据自身的处理能力动态拉取数据，从而控制数据的消费速度，避免由于数据推送带来的压力。

  2. 高效的资源利用：

    • 消费者维护自己读取消息的偏移量（offset），而不是由 Broker 维护。这样大大减轻了 Broker 的负担，使其更加轻量化，提升了系统的整体性能和可扩展性。
Kafka 各组件详解

1. Kafka Producer

  • 定义：Kafka Producer 是使用 Kafka 提供的 SDK 开发的应用程序，它将数据转换为消息，并通过网络发送给 Broker。

  • 消息结构：每条消息表示为一个三元组：<topic, key, message>。

    • topic：消息所属的主题，Kafka 将消息按照主题进行逻辑分区，一个主题可以分布在多个 Broker 上。
    • key：消息的主键，Kafka 根据主键将同一主题下的消息划分到不同的 Partition，默认使用哈希取模算法，用户也可以自定义分区算法。
    • message：消息的值，可以是字符串、JSON 对象，或者经过序列化框架（如 JSON、Avro、Thrift、Protobuf 等）序列化后的对象。

  • 连接 Broker：生产者不需要指定所有 Broker 的地址，只需提供一个或几个初始化 Broker 的地址。Producer 会通过指定的 Broker 获取其他 Broker 的位置信息，并自动实现负载均衡。

2. Kafka Broker

  • 定义：Kafka Broker 是 Kafka 集群中的单个服务器，是实现发布-订阅模型的核心组件。

  • 职责：

    • 接收 Producer 和 Consumer 的请求，并将消息持久化到本地磁盘。
    • 以主题为单位将消息划分为不同的分区（Partition），每个分区可以有多个副本（Replica），以实现容错。
    • 在 Partition 存在多个副本时，选举一个作为 Leader，对外提供读写请求，其余为 Follower，仅同步 Leader 中的数据。

  • 消息顺序：Kafka 保证同一 Topic 下同一 Partition 内的消息有序，但不同 Partition 之间的消息无全局顺序。这意味着消费者从多个 Partition 中读取消息时，可能得到与写入顺序不一致的消息序列。

  • 写入方式：Broker 以追加的方式将消息写到磁盘文件中，消息被赋予唯一整数标识，称为 “offset”。Broker 不维护消费者的 offset，而是由消费者自行维护已读取消息的进度。

3. Kafka Consumer

  • 定义：Kafka Consumer 主动从 Kafka Broker 拉取消息进行处理。

  • offset 管理：每个消费者维护最后一个已读取消息的 offset，并在下一次请求中从该 offset 开始拉取消息。这种基于拉取（pull）的机制大大降低了 Broker 的压力，提高了吞吐率。

  • Consumer Group：多个消费者可以组成一个 Consumer Group，共同读取同一主题中的数据，从而提高数据读取效率。Kafka 会自动为同一 Group 中的消费者分摊负载，并在某个消费者故障时，将其处理的 Partition 转移给其他消费者。

4. ZooKeeper

  • 作用：ZooKeeper 在 Kafka 集群中负责分布式服务的协调。Broker 和 Consumer 都依赖于 ZooKeeper 的服务才能正常工作。

  • Broker 与 ZooKeeper：

    • 所有 Broker 向 ZooKeeper 注册，记录自身位置、健康状态、维护的 Topic、Partition 等信息，以便于其他消费者发现并获取这些数据。
    • 当某个 Consumer 宕掉时，其他 Consumer 可以通过 ZooKeeper 发现故障并自动分摊负载，触发容错机制。

  • Consumer 与 ZooKeeper：

    • Consumer Group 通过 ZooKeeper 保证各个 Consumer 的负载均衡。在某个 Consumer 或 Broker 出现故障时，ZooKeeper 会重新分配负载。
    • Consumer 将最近获取的消息的 offset 写入 ZooKeeper，以便在故障重启后能够从故障前的断点继续读取数据。
Kafka 关键技术点

1. 可控的可靠性级别

  • 发送方式：
    • 同步方式：Producer 在发送数据时等待 Broker 的确认，适合对数据可靠性要求高的场景，但会增加延迟。
    • 异步方式：Producer 不等待 Broker 的确认，快速发送消息，适合对性能要求高的场景，可以通过批处理来提升效率。
  • 消息应答方式：Kafka 允许 Producer 通过 request.required.acks 参数来控制消息应答的级别，平衡写性能与可靠性。常见的应答方式有：
    • 0：Producer 不等待 Broker 的确认，可能导致消息丢失。
    • 1：Leader Broker 确认消息写入后即可返回，可能导致数据丢失，若 Leader 故障则无法恢复。
    • -1（all）：等待所有副本确认，确保消息持久化到所有副本，提供最强的数据可靠性。

2. 数据多副本

  • 副本机制：每个 Topic 中的消息可以存储多个副本，以增强系统的容错能力。Kafka 采用强一致的数据复制策略：

    • 消息首先写入 Leader Partition，然后 Leader 将消息同步到 Follower Partition。
    • Leader Partition 负责对外的读写请求，而 Follower Partition 仅进行数据同步。
    • 在 Leader 出现故障时，其他 Follower 可以通过选举机制提升为 Leader，保证数据的持续可用性。

    强一致：确保了在任何时候，对系统的读操作都能获取到最新的写操作结果。简单来说，当一个节点更新数据后，任何其他节点在访问这份数据时都能立即看到这个更新的结果

3. 高效的持久化机制

  • 数据写入方式：Kafka 直接将消息持久化到磁盘，采用顺序写入策略，提高写入和读取速度。
  • 数据组织方式：结合 offset 进行数据组织，使得 Kafka 能够高效地读写大量数据，适应大数据场景。

4. 数据传输优化：批处理与 Zero-Copy 技术

  • 批处理：将多条消息组合在一起进行发送，减少了单条消息发送的开销，提高了性能。
  • Zero-Copy 技术：减少数据在内存中的复制次数，通常需要四次拷贝的过程被优化为三次拷贝，显著提高了数据发送效率。具体步骤如下：
    1. 内核态的读取缓冲区（read buffer）到内核态的 socket 缓冲区（socket buffer）。
    2. 内核态的 socket 缓冲区直接发送到网卡（NIC buffer）。

5. 可控的消息传递语义 Kafka 提供三种消息传递语义，以适应不同的应用需求：

  • At Most Once：消息发送后不关心接收者是否成功接收，可能导致消息丢失。
  • At Least Once：发送者需等待确认，如果未收到确认，则重发消息，保证消息能被接收，但可能会重复。
  • Exactly Once：保证每条消息只被接收和处理一次，是对可靠性和性能的最佳平衡，但实现较为复杂。

Kafka程序设计

1. Producer 程序设计

  • 创建配置对象：设置Kafka Broker地址、序列化器和ACK策略等参数。
  • 定义分区器（可选）：决定消息分配到哪个Partition的逻辑。
  • 发送数据：创建Producer实例并将消息写入指定的Topic。

2. Consumer 程序设计

  • 创建配置对象：设置Kafka Broker地址、消费者组ID和反序列化器等参数。
  • 创建Consumer Group：实例化Consumer并订阅Topic以读取消息。
  • 拉取消息：循环从Broker中拉取数据进行处理。

日志收集与分析-ELK Stack

1、ELK Stack架构

  • E代表ElasticSearch：搜索和索引(Data Process)
  • L代表LogStash：收集日志和事件数据，甚至可以解析和转换数据(Storage)
  • K代表Kibana：可视化和共享(Visualize)
  • 稍微复杂一些的ELK Stack架构包含了beats，这是一个轻量级的数据采集平台，集合了多种单一用途的数据采集器，可以应对更多样的数据收集和传输任务，具有以下特性：
    • 跟踪数据沿袭：可以从服务器环境中收集日志和指标，对必要元数据进行记录后传输人到ELK Stack中；
    • 可扩展：允许用户自行构建监督某个专用协议的工具。
  • 当处理规模非常庞大的数据时，还可以加入RabbitMQ和Kafka以增加数据传输过程中的缓冲和弹性。
  • 同时还可以加入Nginx来保证数据的安全性。

2、ELK应用 日志会记录一些比较重要的信息，如应用程序的log记录的error，warn级别的log，ELK就是处理日志信息高手。 如果线上环境出了故障，ELK能够立刻准确定位。ELK也经常在运维工作中大放光彩，在应用级别的实时监控，非常适合一些重要核心服务的预警。

ElasticSearch

1、Elasticsearch介绍

  • 一个NoSQL数据库。它基于Lucene搜索引擎，并使用RESTful API构建。它提供简单的部署，可靠性和易管理性，还提供高级查询以执行详细分析并集中存储所有数据
  • Elasticsearch允许存储，搜索和分析大量数据。它主要用做底层引擎，为完成搜索要求的应用程序提供支持。
  • Elasticsearch具备以下特性：
    • 开源搜索服务器使用Java编写
    • 可用于索引任何类型的异构数据
    • 具备带有JSON输出的REST API Web界面
    • 全文检索
    • 近实时（NRT）搜索，实时分析
    • 具备可搜索的JSON文档存储，并允许分片和复制
    • 基于REST和JSON的模式自由（schema-free）分布式文档存储
    • 多语言和地理位置支持

2、Elasticsearch中比较重要的概念

概念 解释
Cluster（集群） 集群是节点的集合，它们共同保存数据并提供连接的索引和搜索功能。
Type（类型） 每个索引里都可以有一个或多个 Type，Type 是索引中的一个逻辑数据分类，一个 Type 下的文档，都有相同的字段（Field）。
Node（节点） 节点表示弹性搜索实例，它是在弹性搜索实例开始时创建的。
Index（索引） 索引是具有类似特征的文档集合，如客户数据、产品目录，在执行索引、搜索、更新和删除操作时有用，一个集群中可以定义多个索引。
Document（文档） 文档是可以被索引的基本信息单位，以JSON键值对表示，如{“user”:“nullcon”},每个文档都与一个类型和一个唯一ID相关联。
Shard（分片） 每个索引都可以拆分为多个分片，以便能够分发数据。分片是索引的原子部分，如果要添加更多节点，则可以将其分发到集群上

3、ElasticSearch特性： 优点：

  • 天生分片、天生集群
  • 天生索引（空间换时间）
  • 支持PB级海量数据实时全文搜索
  • 支持多语言访问，支持TCP和RESTful API两种方式访问

缺点：

  • 不合适做复杂聚合，会影响ES集群的性能
  • 不支持高并发写入数据
  • ES耗CPU和内存资源，需要用高配置的机器来搭建集群，成本高

4、ElasticSearch应用场景

  • 日志分析
  • 信息检索
  • 数据智能

Logstash

1、Logstash 是一个轻量级、开源的日志收集处理框架，可以方便的把分散、多样化的日志搜集起来，并进行自定义过滤分析处理，然后传输到指定位置（如送入 Elasticsearch） Logstash 使用 JRuby 语言编写； Logstash 可以统一来自不同来源的数据，并将数据标准化为想要的格式；允许清理和本地化所有数据，以便对用例进行分析和可视化。

2、Logstash 的设计简单，其功能由三部分组成： Input：数据收集 Filter：数据加工，如过滤，改写等 Output：数据输出

3、Logstash 的特点

  • 使用内部队列将事件传递到每个阶段
  • 允许日志的不同输入
  • 过滤/解析日志

4、Logstash 的优点

  • 几乎可以访问任何数据
  • 可以和多种外部应用整合
  • 支持动态、弹性拓展

5、Logstash 运行逻辑

  • Shipper: 主要用来收集日志数据，负责监控本地日志文件的变化，及时把日志文件的最新内容收集起来，然后经过加工、过滤，输出到 Broker。
  • Broker: 相当于日志Hub，用来连接多个 Shipper 和多个 Indexer。
  • Indexer: 从 Broker 读取文本，经过加工、过滤，输出到指定的介质 (可以是文件、网络、elasticsearch 等) 中。

Kibana

1、Kibana 是一个开源的数据分析可视化平台，可以为 Logstash 和 ElasticSearch 提供的日志数据进行高效的搜索、可视化汇总和多维度分析，还可以与 Elasticsearch 搜索引擎之中的数据进行交互。 它基于浏览器的界面操作可以快速创建动态仪表板，实时监控ElasticSearch的数据状态与更改。 在Kibana中，有不同的方法可以对数据执行搜索。 以下是最常见的搜索类型：

搜索类型 用法
自由文本搜索 用于搜索特定字符串
字段级搜索 用于搜索特定字段中的字符串
逻辑语句 用于将搜索组合成逻辑语句
近似搜索 用于搜索特定字符的近似项

2、Kinbana 的优点：

  • 强大的前端仪表板，能够可视化集群的索引信息
  • 实现索引信息的实时搜索
  • 可以搜索，查看和与 Elasticsearch 中存储的数据进行交互
  • 对数据执行查询并可视化图表，表格和映射中的结果
  • 可配置的仪表板，用于在 elasticsearch 中对日志记录日志进行切片和切块
  • 能够以图表，图表等形式提供历史数据
  • 实时仪表板，可轻松配置
  • 实现索引信息的实时搜索

商业化大数据解决方案-Splunk

1、Splunk是什么？

  • 面向机器数据的全文搜索引擎（使用搜索引擎的方式处理数据；支持海量级数据处理）
  • 准实时的日志处理平台
  • 基于时间序列的索引器
  • 大数据分析平台

2、Splunk特性

  • 数据摄取（data ingestion）
  • 数据索引（data indexing）
  • 数据搜索（data searching）
  • 使用警报（using alert）
  • 仪表盘（dashboard）
  • 数据模型（ data model）

3、Splunk应用场景

  • IT运营
  • SIME（Security Information and Management）
  • 物联网

网络数据采集-爬虫

1、网络数据采集

2、爬虫：通过程序代码模拟浏览器向网站发起请求，把站点（服务器）返回的HTML代码/JSON数据/二进制数据（图片、视频） 爬取到本地，进而通过解析代码分析并提取自己需要的数据；（若将爬虫比喻为蜘蛛，互联网将是一张蜘蛛网）

3、网络爬虫原理

  • 网络爬虫是一种按照一定的规则，自动地抓取web信息的程序或者脚本
  • 网络爬虫可以自动采集所有其能够访问到的页面内容，为搜索引擎和大数据分析提供数据来源。
  • 从功能上讲，爬虫一般数据采集，处理和存储三部分功能

4、网络爬虫原理 URL的抓取 网页的遍历 构造URL队列

5、网络爬虫工作流程

  • 初始时将预先设定的种子URL放入待抓取URL队列。
  • 从待抓取队列中取出URL，进行DNS解析并下载网页内容，然后放入已抓取URL队列。
  • 从已抓取队列中抽取出新的URL放入待抓取队列，重复步骤二直到定停
