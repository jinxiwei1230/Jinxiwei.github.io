9个软件生命周期模型

1、瀑布模型

  • 定义阶段 2

  • 开发阶段 3

  • 维护阶段 1

瀑布模型中的每一个开发活动具有下列特征

  1. 本活动的工作对象来自于上一项活动的输出（上一阶段输出作为这一阶段输入）
  2. 根据本阶段的活动规程执行相应的任务（每个阶段根据活动规程执行）
  3. 产生本阶段活动相关产出—软件工件，作为下一活动的输入（输出作为下一个活动输入）
  4. 对本阶段活动执行情况进行评审（每个阶段评审）
优点
  • 阶段划分降低软件开发复杂度，提高软件开发过程透明度，便于将软件工程过程和软件管理过程融合在一起，从而提高软件开发过程的可管理性
  • 推迟软件实现，强调软件实现之前必须进行分析和设计工作
  • 以阶段评审和文档控制对开发过程进行指导，保证阶段之间的正确衔接，及时发现并纠正开发过程中存在的缺陷
缺点
  • 缺乏灵活性，无法解决需求不明确或不准确的项目，只适合于需求明确的项目
  • 风险控制能力较弱，成品时间长。风险和错误只有在测试阶段才能发现，返工导致延期
  • 文档驱动，增大工作量

2、V模型和W模型

  • V重视测试，将测试分等级
  • W增加了确认和验证内容，并贯穿整个软件生命周期

3、原型方法

不断试错，不断改进

原型：产品原始模型，软件原型是一个可运行的早期版本，反映最终系统的部分重要特性

  1. 获得一组基本的需求说明，快速分析构造出一个小型的软件系统，满足用户的基本要求；
  2. 用户试用原型系统，对其进行反应和评价；
  3. 开发者根据用户意见对原型进行改进，获得新的原型版本；
  4. 周而复始，直到产品满足用户的要求。

原型的种类（目的）

  1. 探索型：弄清对目标系统的要求
  2. **实验型：**系统实现前考察系统的可行性
  3. **进化型：**将原型扩展到开发过程，通过原型开发逐步实现所有系统功能。

原型的使用策略

  • 废弃策略：探索型和实验型
  • 追加策略：进化型

优点

  • 有助于增进软件人员和用户对系统服务需求的理解
  • 提供了一种有力的学习手段
  • 容易确定系统的性能，服务的可用性，设计的可行性和产品的结果
  • 原型的最终版本可作为最终产品的一部分

缺点

  • 文档容易本忽略
  • 建立原型的许多工作会被浪费掉
  • 项目难以规划和管理

演化模型（原型方法的实践）

第一次：试验开发，目的是探索可行性，弄清楚项目的需求。第一次得到的试验性产品称为“原型”。

第二次：在第一次的原型基础上进行开发，从而获得较为满意的软件产品。

针对需求不明确的软件项目

缺点

  • 抛弃瀑布模型文档控制的优点，软件开发过程不透明
  • 探索式演化模型可能会导致最后的系统结构较差
  • 可能会用到一些不成熟、不符合主流、不符合要求的工具和技术

增量模型

结合了瀑布模型和演化模型的优点

  1. 渐进式开发：系统被分解为多个增量(increment)，每个增量都是一个可交付的产品部分
  2. 需求逐步提出：允许客户的需求分阶段提出，而不是在项目开始时就完全确定
  3. 体系结构稳定性：所有增量的开发都基于一个稳定的系统架构
工作流程
  1. 需求框架定义：客户首先定义整体需求框架
  2. 优先级确定：客户和开发团队共同确定需求的实现优先级
  3. 体系结构设计：基于核心需求和性能要求设计稳定的系统架构
  4. 增量实现：按优先级逐步实现各个增量，每个增量都是可工作的产品部分
  5. 增量集成：将新完成的增量集成到现有系统中，确保不影响整体架构

优点

  • 增强客户使用系统的信心，逐步提出对后续增量的需求
  • 项目总体失败的风险较低
  • 增量从高到低的优先级确定保证了系统重要功能部分的可靠性
  • 同一体系结构提高了系统的稳定性和可维护性

缺点

  • 增量的粒度选择问题
  • 确定所有的基本业务比较困难

螺旋模型

  1. 风险驱动：将风险分析作为核心环节，贯穿整个开发过程
  2. 迭代演进：通过多次循环迭代逐步完善系统
  3. 多原型开发：需要开发内容逐步丰富的多个原型，而非单一原型
  4. 综合方法：结合了瀑布模型的系统性和演化模型的灵活性
四个象限活动

  1. 制定计划

    确定软件目标与约束条件、评估备选技术方案，确定资源、进度等限制条件

  2. 风险分析

    识别潜在风险因素、评估风险发生的概率和影响、制定风险缓解或规避策略、必要时终止高风险项目

  3. 实施工程

    根据当前迭代目标进行开发，可能包括需求分析、设计、编码、测试等活动，产生可验证的工作产品

  4. 客户评估

    客户对当前迭代成果进行评价、提出修改建议和新需求，为下一轮迭代提供输入

最适合：

  • 需求不明确的大型复杂系统
  • 高风险项目
  • 技术方案不确定的创新项目
  • 长期演进的关键任务系统

喷泉模型

  1. 迭代性：
    • 开发过程是多次重复、逐步演进的过程
    • 各阶段可以反复进行，而非线性顺序
    • 允许不断精化和完善系统
  2. 无间隙性：
    • 各开发阶段之间没有严格的界限
    • 分析和设计结果可以自然复用
    • 活动之间可以流畅过渡和回溯

构件组装模型

构件组装模型本质上是演化的，开发过程是迭代的。

由五个阶段组成：

  • 需求定义和分析
  • 软件体系结构设计
  • 构件开发
  • 应用软件构造
  • 测试和发布

软件的开发过程步骤如下：

  • (1)定义和分析需求；
  • (2)标识本项目需要什么构件；
  • (3)从库中查找构件或相似的构件；
  • (4)如果可用转(5)，否则自行开发或修改，确认后入库；
  • (5)构造为新系统作第m次迭代；
  • (6)测试、确认。

快速应用开发（RAD）模型

5个阶段

  1. 业务建模：分析业务流程（数据流图DFD）
  2. 数据建模：设计数据结构（E-R图）
  3. 过程建模：定义业务逻辑（细化处理流程）
  4. 应用生成：用4GL/组件快速构建（80%重用+20%开发）
  5. 测试迭代：重点测新组件，持续优化

新型软件生命周期模型

统一软件开发过程（RUP）

RUP既是一种软件生命周期模型，又是一种支持面向对象软件开发的工具

方法，工具，过程

RUP的基本结构：二维软件开发模型

横轴：时间轴（阶段+迭代） 将整个生命周期过程分为4个阶段，每个阶段特有的里程碑是该阶段结束的标志，每个阶段内又划分为不同的迭代（动态结构）

**纵轴：内容轴（活动+工件）**包括活动、活动产出的工件、活动的执行角色以及活动执行的工作流（静态结构）

四个开发阶段

每个阶段以 里程碑（Milestone） 结束，包含多次迭代：

阶段 目标 里程碑交付物 关键评审点
初始阶段 (Inception) 确定项目范围、验收规范、风险、资源估计、阶段计划 文档、原始用例模型、业务风险评估、原型 正确理解用例需求、项目风险评估合理、阶段计划可行
细化阶段 (Elaboration) 建立适合需求的软件体系结构基础，编制项目计划，解决高风险需求 风险分析文档、体系结构基线、可执行原型、修订计划 软件体系结构的稳定性、确认高风险的业务需求和技术机制已经解决
构造阶段 (Construction) 开发剩余功能，集成为产品测试 可运行软件产品、用户手册 确定软件、环境、用户是否可以开始系统的运行
移交阶段 (Transition) 产品交付与用户反馈调整 最终版本、维护手册 是否达到发布标准？

RUP的迭代增量开发思想

RUP是以用例为驱动，软件体系结构为核心，应用迭代及增量的新型软件生命周期模型

RUP是融合了喷泉模型和增量模型的一种综合生命周期模型

6个过程工作流（贯穿各阶段）：商业建模 → 需求 → 分析设计 → 实现 → 测试 → 部署

3个支持工作流：配置管理 、 项目管理 、 环境搭建

RUP 最佳实践
  • 早期解决高风险问题：在细化阶段确定核心架构
  • 持续验证质量：频繁测试（单元测试、集成测试）
  • 用户参与评估：每个迭代收集反馈
  • 用例驱动开发：需求→设计→代码的全程追踪
  • 可视化建模：使用 UML 统一表达（如用例图、类图）
  • 严格变更管理：控制需求变更影响

敏捷开发

敏捷宣言（思想，不是软件生命周期模型）
  • 个体和交互胜过过程和工具
  • 可以工作的软件胜过面面俱到的文档
  • 客户合作胜过合同谈判
  • 相应变化胜过遵循计划

敏捷方法的主要特点就是具有快速以及灵活的响应变更能力

  • 以人为本：强调团队协作与客户参与
  • 迭代渐进：项目拆分为可独立运行的子项目，持续交付可运行版本
  • 拥抱变化：通过短周期迭代适应需求变更
极限编程（XP）
  • 快速的反馈，大量而迅速的交流，经过保证的测试来最大限度的满足用户的需求
  • 强调用户满意，开发人员可以对需求的变化做出快速的反应
  • 工作环境：所有人都在同一个开放的环境中工作
  • 配对编程，严格遵守编程规范，任何人都可以修改其他人写的程序，修改后要确定新程序能通过单元测试
XP需求分析：User Story驱动
  • 协作拆分需求：开发人员与客户共同将需求分解为小模块（User Story），记录在Story Card上
  • 动态调整：根据实际组合或拆分模块，确保灵活性
  • 优先级排序：客户按商业价值排序，开发团队评估技术风险
  • 验收测试前置：客户为每个模块定义验收标准（测试用例）

​ 核心目标：快速响应变更，确保需求价值最大化
