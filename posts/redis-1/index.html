1 键值数据库概述

1. 键值数据库技术特点

核心优势
  • 高性能：
    • 哈希算法关联Key-Value，时间复杂度O(1)的查询效率。
  • 操作简单：
    • 提供丰富API，支持增删改查、范围查询、集合运算（并集/交集/差集）。
  • 多数据结构支持：
    • 字符串、双向链表、Hash表、集合、有序集合等。
    • 值可为二进制、文本、JSON等格式。
高级特性
  • Key过期管理：支持TTL（Time to Live）。
  • 持久化：内存数据可持久化到磁盘，防止数据丢失。
  • 事务：
    • 单命令原子性执行，支持批量操作的事务管理。
  • 扩展性：
    • 分片技术实现水平扩展。
  • 高可用：
    • 主从复制、读写分离、哨兵机制保障容错性。
  • 多语言API：支持多种编程语言接口。

2. Redis高可用架构

  • 机制：
    • 主从集群、读写分离、哨兵监控、增量复制。
  • 节点角色：
    • 主节点（Master）与从节点（Replica）。
  • 应用场景：
    • 通过副本节点提升读性能，主从切换保障故障恢复。

3. 对比：Amazon DynamoDB

  • 核心能力：
    • 完全托管，毫秒级延迟（<10ms）。
    • 内置安全、备份、恢复机制。
  • 数据模型：
    • 项目：主键/复合键 + 不限数量的属性（总大小≤400KB）。
    • 表：无限制的数据项集合（类似关系型数据库的表）。

2 键值数据存储逻辑架构

1. 键值存储核心逻辑

  • 数据模型：
    • 基于关联数组（键值对集合），每条记录可包含不同属性，体现NoSQL模式灵活性。
    • 键（Key）：唯一标识记录，支持快速读写单行数据。
  • 基本操作：
    操作 命令示例 说明
    set set(key, value) 存储/覆盖键值数据
    get get(key) 读取键值数据（键不存在时报错）
    del del(key) 删除键值数据
    • 注：不同数据库的命令名称可能差异（如Redis用SET/GET/DEL）

2. Redis键值存储实现

内存结构分层

  1. dictEntry

    • 包含：
      • 指向Key的指针（SDS字符串对象）
      • 指向Value的指针（RedisObject形式）
      • 指向下一个dictEntry的指针（哈希冲突时链式存储）

  2. RedisObject（值对象的元数据）

typedef struct redisObject {
    unsigned type:4;     // 数据类型（如字符串/集合等）
    unsigned encoding:4; // 底层编码实现（如int/哈希表等）
    unsigned lru:24;     // 最后一次访问时间（用于LRU淘汰）
    int refcount;        // 引用计数（内存回收）
    void *ptr;           // 指向实际数据的指针
} robj;
  • type：应用层数据类型（如2表示集合）。
  • encoding：底层实现编码（优化存储效率）。
  1. 具体数据对象
    • 如SDS字符串、双向链表、哈希表等。

3. Key管理机制

  • 键的特性：
    • 唯一性：数据分区的依据。
    • 命名规范：用冒号分段表示关联性（如表名:主键:字段名）。
  • 过期与清除：
    • TTL（Time to Live）：设置键的有效期。
    • 内存超限处理：
      • 清除策略：
        • 惰性删除：访问时检查过期，立即删除。
        • 定期删除：周期性扫描并清理过期键。

4. Redis六大数据类型

数据类型 应用场景 特点
String 缓存、计数器 二进制安全，可存文本/数字/JSON
List 消息队列、日志 双向链表，支持头尾操作
Set 标签、去重 无序集合，支持交并差运算
Hash 对象属性存储 字段-值映射表
ZSet 排行榜、优先级队列 有序集合，按分值排序
Stream 消息流（5.0+） 持久化消息队列，支持消费者组

5. 关键设计思想

  • 性能优化：
    • 哈希表O(1)查询 + 内存高效编码（如ziplist压缩列表）。
  • 扩展性：
    • 通过键的分片（如一致性哈希）实现水平扩展。
  • 场景适配：
    • 每种数据结构针对特定高频场景（如ZSet用于排行榜）。

附：RedisObject类型与编码示例

type类型 常量名 encoding编码 示例
0 REDIS_STRING REDIS_ENCODING_INT 整数"123"
1 REDIS_LIST REDIS_ENCODING_LINKEDLIST 双向链表
2 REDIS_SET REDIS_ENCODING_HT 哈希表实现的集合

1. String（字符串）

核心特性
  • 底层实现：简单动态字符串（SDS，Simple Dynamic String）
  • 二进制安全：
    • 不以 \0 结尾，可存储任意二进制数据（如图片、音频、序列化对象等）。
    • 最大容量：512MB。
  • 应用场景：
    • 缓存（用户信息、配置）、计数器（微博粉丝数、商品销量）。
SDS内存结构
struct sdshdrX {
    T len;          // 字符串实际长度
    T alloc;        // 预分配的总空间（避免频繁扩容）
    unsigned char flags;  // 类型标记（sdshdr5/8/16/32/64）
    char buf[];     // 存储数据的柔性数组
};
  • 优化策略：
    • 空间预分配：扩容时多分配冗余空间，减少内存重分配次数。
    • 惰性空间释放：缩容时不立即释放内存，避免频繁缩容开销。
  • 子类型：
    类型 说明
    sdshdr5 仅含 flags 和 buf，适用于极短字符串
    sdshdr8/16/32/64 根据长度选择不同位宽的 len 和 alloc，节省内存
操作示例
# 存储用户访问量
SET user:1000:visits 42
# 自增计数
INCR user:1000:visits  # 结果: 43
# 存储JSON数据
SET user:1000 '{"name":"Alice","city":"Beijing"}'

2. List（列表）

核心特性
  • 底层实现：双向链表（支持头尾高效操作）
  • 有序性：按插入顺序排序。
  • 最大长度：2³² - 1 个元素（约40亿）。
  • 应用场景：
    • 消息队列、最新评论列表、最近登录用户记录。
数据结构设计
  • 双向链表节点： 
    typedef struct listNode {
    struct listNode *prev;  // 前驱节点
    struct listNode *next;  // 后继节点
    void *value;           // 存储的值（SDS字符串）
} listNode;
  • 快速头尾访问：
    • 通过 head 和 tail 指针实现 O(1) 复杂度操作。
操作示例
# 模拟栈（后进先出）
LPUSH stack "task1"  # 左侧插入
LPOP stack           # 左侧弹出 → "task1"

# 模拟队列（先进先出）
LPUSH queue "msg1"   # 左侧插入
RPOP queue           # 右侧弹出 → "msg1"

# 存储最近3个访问用户
LPUSH latest_users "u1" "u2" "u3"  
LRANGE latest_users 0 2  # 获取范围 → 1)"u3" 2)"u2" 3)"u1"
实战场景
  • 消息队列：
    • 生产者 LPUSH 消息，消费者 BRPOP 阻塞获取。
  • 最新N条记录：
    • 通过 LTRIM 控制列表长度（如保留最近10条）。

3. Set（集合）

核心特性
  • 无序性：元素无顺序，通过哈希表实现（O(1)复杂度操作）。
  • 唯一性：自动去重，重复插入返回 0。
  • 容量限制：最多存储 2³² - 1 个元素（约40亿）。
  • 应用场景：标签系统、好友关系、唯一性校验。
操作示例
# 添加元素（成功返回1，重复返回0）
SADD tags "redis" "database"  # → (integer) 2
SADD tags "redis"             # → (integer) 0

# 查看所有元素
SMEMBERS tags                 # → 1) "database" 2) "redis"

# 集合运算（交/并/差集）
SINTER set1 set2              # 交集
SUNION set1 set2              # 并集
SDIFF set1 set2               # 差集
底层实现
  • 哈希表：通过 dict 结构实现，仅存储键（无值），利用哈希特性快速判重。

4. Hash（哈希表）

核心特性
  • 结构：键值对集合（field-value），适合存储对象属性。
  • 嵌套映射：外层Key → 内层Map（field为属性名，value为属性值）。
  • 容量限制：每个Hash可存储 2³² - 1 个键值对。
  • 应用场景：用户信息、商品详情、配置项。
操作示例
# 批量设置字段
HMSET user:1000 name "Alice" age 25 city "Beijing"  # → "OK"

# 获取单个字段
HGET user:1000 name           # → "Alice"

# 获取所有字段值
HVALS user:1000               # → 1) "Alice" 2) "25" 3) "Beijing"

# 原子操作（如递增）
HINCRBY user:1000 age 1       # → 26
底层优化
  • ziplist：字段较少时使用连续内存压缩存储。
  • 哈希表：字段较多时转为哈希表提升查询效率。

5. ZSet（有序集合）

核心特性
  • 排序依据：每个元素关联一个 score（double类型），按score排序。
  • 唯一性：元素唯一，但 score 可重复。
  • 应用场景：排行榜、优先级队列、带权重的任务调度。
操作示例
# 添加元素（ZADD key score member）
ZADD leaderboard 100 "PlayerA" 200 "PlayerB"  # → (integer) 2

# 按score范围查询
ZRANGEBYSCORE leaderboard 0 150 WITHSCORES  # → 1) "PlayerA" 2) "100"

# 获取排名（降序）
ZREVRANK leaderboard "PlayerB"               # → 0（第一名）
底层实现
  • 跳跃表（zskiplist）：支持O(logN)复杂度的范围查询。
  • 哈希表：辅助快速判断元素是否存在。

6. Stream（流）

核心特性
  • 消息队列：持久化的多播消息流，支持消费者组（类似Kafka）。
  • 消息结构：
    • 唯一ID（含时间戳）：如 1526569415632-0。
    • 内容：键值对形式（可扩展）。
  • 应用场景：事件日志、实时消息推送、异步任务队列。
操作示例
# 添加消息
XADD orders * product_id 1003 quantity 2  # → "1651234567890-0"

# 创建消费者组
XGROUP CREATE orders group1 $             # → "OK"

# 消费者读取消息
XREADGROUP GROUP group1 consumer1 COUNT 1 STREAMS orders >  
# → 1) 1) "orders"  
#    2) 1) 1) "1651234567890-0"  
#          2) 1) "product_id" 2) "1003" 3) "quantity" 4) "2"

# 确认消息消费
XACK orders group1 "1651234567890-0"      # → (integer) 1
关键机制
  • 消费者组：
    • 组间数据独立，组内消费者竞争消费（每条消息仅被组内一个消费者处理）。
    • Pending_ids：记录未ACK的消息ID，确保消息不丢失。
  • 持久化：重启后消息保留，支持断点续传。

3.1 Redis持久化管理

1. 持久化核心机制

方式 原理 文件类型 触发条件
RDB 内存数据快照（全量备份） 二进制文件（.rdb） 定时触发或手动命令
AOF 记录写操作日志（增量备份） 文本文件（.aof） 实时/每秒同步
无 纯内存模式（类似Memcached） 无 禁用持久化配置

2. RDB（Redis Database）

核心特性
  • 全量备份：保存某一时间点的完整数据集。
  • 二进制格式：紧凑高效，适合灾难恢复。
  • Fork子进程：主进程不阻塞，通过写时复制（COW）技术保证数据一致性。
配置参数
save <seconds> <changes>  # 自动触发条件（可配置多条）
示例（Redis7默认）：
save 3600 1    # 1小时内至少1次修改
save 300 100   # 5分钟内至少100次修改
save 60 10000  # 1分钟内至少10000次修改
触发方式
命令 特点 使用场景
SAVE 阻塞主进程，同步生成RDB 维护时段低峰期
BGSAVE 非阻塞，子进程异步生成RDB 生产环境首选
优劣势对比
优势 劣势
文件小，加载速度快 可能丢失最后一次快照后的数据
备份方便，适合冷备 大数据量时fork子进程耗内存
对性能影响小（后台运行） 频繁保存影响IO性能

3. AOF（Append Only File）

核心特性
  • 日志追加：记录所有写操作命令（文本格式）。
  • 重写机制：压缩冗余命令（BGREWRITEAOF）。
  • 多文件支持（Redis7+）：拆分AOF文件提升管理效率。
同步策略
配置 数据安全性 性能影响
appendfsync always 最高（每条命令同步） 最差（频繁磁盘IO）
appendfsync everysec 适中（每秒同步） 平衡（推荐）
appendfsync no 最低（依赖OS缓冲） 最佳（风险最高）
优劣势对比
优势 劣势
数据丢失少（可配置秒级同步） 文件体积大
可读性强（文本格式） 恢复速度慢（需重放命令）
支持重写压缩历史命令 高并发下可能阻塞主线程

4. RDB vs AOF对比

维度 RDB AOF
数据完整性 可能丢失最后一次快照后数据 根据配置可接近零丢失
恢复速度 快（直接加载二进制） 慢（需逐条执行命令）
文件大小 小（二进制压缩） 大（文本日志）
适用场景 灾难恢复、定期备份 高数据安全要求、实时持久化

5. 混合持久化（Redis4+）

  • 配置：aof-use-rdb-preamble yes
  • 原理：AOF重写时先以RDB格式保存全量数据，再追加增量命令。
  • 优势：
    • 结合RDB快速加载和AOF低丢失特性。
    • 重启时优先加载RDB部分，再重放AOF日志。

6. 生产建议

  1. 数据安全优先：
    • 启用AOF + appendfsync everysec + RDB定时备份。
  2. 性能优先：
    • 禁用AOF，仅用RDB（注意数据丢失风险）。
  3. 混合模式（推荐）：
    • Redis4+版本开启混合持久化，平衡性能与安全性。
关键总结
  • RDB：适合备份与快速恢复，容忍分钟级数据丢失。
  • AOF：适合高安全性场景，需权衡IO性能。
  • 监控命令：
    • INFO persistence 查看持久化状态。
    • LASTSAVE 检查最后一次RDB成功时间。

3.2 Redis分区机制

1. 分区核心概念

  • 定义：将大数据集分割到多个Redis实例，每个实例仅存储键的子集。
  • 目的：
    • 突破单机内存/性能瓶颈。
    • 实现水平扩展与负载均衡。

2. 分区方案对比

类型 原理 优点 缺点
范围分区 按键的区间范围映射到实例（如1-1000→A） 直观，适合有序数据 需维护映射表，扩展性差
哈希分区 对键哈希取模（如crc32(key)%4） 数据分布均匀，扩展灵活 扩缩容需数据迁移
虚拟槽分区 预分16384个槽，键映射到槽再分配实例 无中心化，动态扩缩容 Redis Cluster专属实现

3. 分区实现角色

角色类型 工作流程 代表工具 适用场景
客户端分区 客户端直接计算目标节点并通信 Redis客户端库 简单架构，需一致性哈希
代理分区 客户端→代理→节点（代理决定路由） Twemproxy 解耦客户端与集群
查询路由 客户端随机请求节点，节点间转发请求 Redis Cluster 原生集群方案，高可用

4. 分区关键问题

  • 数据迁移：
    • 扩缩容时需重新分配键，传统哈希分区需全量迁移。
    • Redis Cluster解决方案：采用虚拟槽，仅迁移受影响槽的数据。
  • 多键操作限制：
    • 跨节点的多键操作（如MGET）需客户端聚合结果。
  • 事务支持：
    • 仅单节点事务保证原子性，跨节点需分布式事务补偿。

5. 生产建议

  1. 选型策略：
    • 中小规模：代理分区（Twemproxy + 一致性哈希）。
    • 大规模：Redis Cluster（虚拟槽分区 + 去中心化）。
  2. 监控指标：
    • 节点负载均衡性（INFO keyspace）。
    • 槽迁移进度（CLUSTER SLOTS）。
  3. 扩缩容步骤： 
    # Redis Cluster添加节点
redis-cli --cluster add-node new_node:6379 existing_node:6379
# 重新分配槽
redis-cli --cluster reshard existing_node:6379

3.3 Redis集群监控（哨兵机制）

1. 哨兵核心功能

功能 说明
监控 持续检查Master/Replica运行状态
通知 通过API向管理员发送故障报警
自动故障转移 Master失效时自动选举新Master并重新配置集群
配置中心 客户端通过哨兵获取当前有效的Master地址

2. 哨兵集群架构

  • 部署要求：
    • 至少3个哨兵节点（防止脑裂）
    • 奇数节点部署（基于Raft选举算法）
  • 拓扑结构： 
    graph TD
  S1[哨兵1] --> M[Master]
  S2[哨兵2] --> M
  S3[哨兵3] --> M
  M --> R1[Replica1]
  M --> R2[Replica2]
  R1 --> R3[Replica3]

3. 故障检测流程

3.1 主观下线(SDOWN)
  • 触发条件：
    • 哨兵节点通过PING检测到实例超时无响应（默认30秒）
  • 特点：
    • 单哨兵节点的局部判断
3.2 客观下线(ODOWN)
  • 触发条件：
    • 超过半数哨兵（quorum配置）确认Master主观下线
    • 执行命令：SENTINEL is-master-down-by-addr
  • 特点：
    • 仅针对Master节点
    • 触发故障转移的前置条件

4. 故障转移流程

4.1 领导者选举
  • 算法：Raft协议简化版
  • 步骤：
    1. 每个哨兵节点向其他节点发送投票请求
    2. 节点优先响应最先到达的请求（先到先得）
    3. 获得多数票（≥ N/2+1）的哨兵成为Leader
4.2 新Master选举标准
优先级 评估指标 说明
1 slave-priority配置值（越小越优先） 默认100，0表示不参与选举
2 复制偏移量（越大数据越新） 通过INFO replication获取
3 进程ID（越小越优先） 最终仲裁条件
4.3 集群重构
  1. 升主操作：哨兵Leader向目标Replica发送SLAVEOF NO ONE
  2. 重配从节点：向其他Replica发送SLAVEOF new_master
  3. 配置持久化：对所有节点执行CONFIG REWRITE
  4. 旧Master恢复：若原Master重新上线，会被降级为Replica

5. 哨兵定时任务

任务 频率 命令/协议 目的
节点监控 1秒 PING 检测节点存活状态
拓扑同步 10秒 INFO replication 获取集群节点关系
哨兵通信 2秒 发布订阅频道__sentinel__ 同步哨兵节点间的认知

  • 局限性：
    • 单Master写入性能瓶颈
    • 数据量受单机内存限制
  • 解决方案：
    • 升级为Redis Cluster模式（支持数据分片）
    • 分片逻辑：

def get_shard(key):
    slot = crc16(key) % 16384  # Redis Cluster使用16384个槽

关键总结

  1. 哨兵集群是Redis高可用的核心组件，需至少部署3节点。
  2. 故障转移依赖Raft选举和优先级策略，需合理配置slave-priority。
  3. 监控粒度通过down-after-milliseconds调整，平衡敏感性与误报率。
  4. 大规模场景应使用Redis Cluster，哨兵模式适合中小规模高可用需求.
