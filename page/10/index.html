软件工程概述

计算机软件

1、软件的定义

软件是包括程序，数据及其相关文档的完整集合

  • 程序是按事先设计的功能和性能要求执行的指令序列；
  • 数据是使程序能正常操纵信息的数据结构；
  • 文档是与程序开发，维护和使用有关的图文材料。

2、软件特点

  • 逻辑实体，具有抽象性，无法看到具体形态
  • 软件的开发是一种逻辑思维成熟的过程，无明显制造过程
  • 在软件的运行和使用过程中，没有硬件那样的机械磨损，老化问题，但却存在退化问题
  • 软件的开发过程依然很原始，至今尚未完全摆脱手工艺的开发形式
  • 软件是高度复杂的逻辑体。
  • 软件的开发和运行常常受到计算机系统的限制，对计算机系统有着不同程度的依赖性。尽量提高软件的可移植性。
  • 软件成本相当昂贵。软件的研制工作需要投入大量的、复杂的、高强度的脑力劳动。
  • 相当多的软件工作涉及到社会因素。

软件的发展和软件危机

软件技术发展第二阶段（60～70年代），随着硬件技术的进步，计算机应用范围扩大，但软件技术一直未能满足形式发展的要求，软件开发的高成本与软件产品的低质量之间的尖锐矛盾，导致软件危机问题出现。

软件危机（Software Crisis）：指由于落后的软件生产方式无法满足迅速增长的计算机软件需求，从而导致软件开发与维护过程中出现一系列严重问题的现象。

软件危机主要有以下几方面的表现：

  • 软件开发计划难以制订。
  • 软件开发费用和进度失控。
  • 软件产品无法让用户满意。
  • 软件产品的质量难以保证。
  • 软件通常没有适当的文档资料。
  • 软件通常是不可维护的。
  • 软件成本在计算机系统总成本中所占比例逐年上升。

软件危机的解决途径

1、软件危机产生的内在原因
  • 软件生产本身存在复杂性
  • 软件开发和维护所使用的方法不合理
2、软件开发需要对程序设计方法等问题进行研究，也需要对软件的需求、设计、测试、维护和管理等方法进行研究。

软件工程

主要思想：按照工程化的原理、原则和方法开发、运行、维护软件。

软件工程三要素

  • 方法：解决 “如何做”，涵盖从计划到维护等多项软件开发任务
  • 工具：提供自动或半自动支撑环境，如 CASE，辅助开发工作。
  • 过程：整合方法和工具，明确方法使用顺序、交付文档要求、管理方式及各阶段里程碑 ，实现高效开发。

软件工程的目标

在给定成本、进度的前提下，开发满足用户需求且具有可修改性、可靠性、有效性、可理解性、可重用性、可维护性、可适应性、可移植性、可追踪行、可相互操作性的软件产品

软件工程四条基本原则

  • 选取适宜的开发模型
  • 采用合适的设计方法
  • 提供高质量的工程支持
  • 重视开发过程的管理

软件工程一般原理：包含抽象、信息隐藏、模块化、局部化、确定性、一致性、完备性、可验证性。

软件工程基本原理：

  • 分阶段的生命周期计划严格管理，通过多种计划保障项目推进；
  • 阶段评审可尽早发现并排除错误；
  • 严格的产品控制能降低需求变动影响；
  • 现代程序设计技术可提高开发和维护效率；
  • 清楚审查结果有助于把控项目质量；
  • 人员少而精能提升开发效果；
  • 不断改进实践可推动软件工程发展

软件工程知识体系

  • 统一认知：促进全球对软件工程形成一致观点，消除不同地区、组织在理解上的差异，推动行业共识的形成。
  • 明确学科关系：清晰界定软件工程与计算机科学、项目管理、计算机工程、数学等相关学科的关联与界限，让从业者和学习者能准确把握软件工程在多学科领域中的定位。
  • 确定学科内容：系统归纳软件工程学科涵盖的具体内容，构建全面且有条理的知识框架。
  • 梳理知识专题：对软件工程本体知识进行细分，明确各个专题，方便学习者深入探究和掌握不同知识点。
  • 支持教育与认证：为软件工程相关课程的设计以及职业资格认证材料的编写提供坚实基础，助力培养专业人才和规范行业标准 。

戴明环

软件工程过程的6个基本活动

  • P 制定计划
  • D 需求分析
  • D 设计
  • D 程序编码
  • C 测试
  • A 运行维护

9个软件生命周期模型

1、瀑布模型

  • 定义阶段 2

  • 开发阶段 3

  • 维护阶段 1

瀑布模型中的每一个开发活动具有下列特征

  1. 本活动的工作对象来自于上一项活动的输出（上一阶段输出作为这一阶段输入）
  2. 根据本阶段的活动规程执行相应的任务（每个阶段根据活动规程执行）
  3. 产生本阶段活动相关产出—软件工件，作为下一活动的输入（输出作为下一个活动输入）
  4. 对本阶段活动执行情况进行评审（每个阶段评审）
优点
  • 阶段划分降低软件开发复杂度，提高软件开发过程透明度，便于将软件工程过程和软件管理过程融合在一起，从而提高软件开发过程的可管理性
  • 推迟软件实现，强调软件实现之前必须进行分析和设计工作
  • 以阶段评审和文档控制对开发过程进行指导，保证阶段之间的正确衔接，及时发现并纠正开发过程中存在的缺陷
缺点
  • 缺乏灵活性，无法解决需求不明确或不准确的项目，只适合于需求明确的项目
  • 风险控制能力较弱，成品时间长。风险和错误只有在测试阶段才能发现，返工导致延期
  • 文档驱动，增大工作量

2、V模型和W模型

  • V重视测试，将测试分等级
  • W增加了确认和验证内容，并贯穿整个软件生命周期

软件需求分析

系统分析

作用

探索软件项目的目标、市场预期、主要的技术指标（立项参考）

所有人参与：硬件工程师、软件工程师、数据库专家

可行性分析

  • 经济可行性
  • 技术可行性
  • 法律可行性
  • 方案的选择

需求定义

  1. 需求的定义：软件开发人员通过与软件产品的拥有者、使用者交流调研，获取业务相关信息，整理分析后得出软件产品功能、性能等指标的规格描述。
  2. 需求的不确定性：需求具有不确定性，这恰恰体现了其重要性。需求分析的质量对软件产品质量影响巨大，准确编写需求难度大，若需求有误，会给软件系统带来严重损害，且后期修改困难。

软件需求分析的目标和任务

任务

研究一种无二义性的表达工具，能被软件人员和用户双方都接受，严格、形式化表达需求

准确定义新系统的目标，回答系统必须做什么的问题，编写需求规格说明书

目标

借助于当前系统的逻辑模型，解决目标系统做什么的问题

需求分析的必要性

  • 桥梁作用：在系统需求分析和软件设计间搭建桥梁，基于系统分析，让开发人员进一步明确软件功能、性能，确定软件与其他系统元素的接口及约束条件。
  • 构建分析模型：帮助开发人员细化关键问题，构建数据、功能和行为模型，这些模型是设计模型的基石。
  • 提供评估依据：需求规格说明书为软件测试人员和用户评估软件质量提供了标准，同时能精准呈现用户对系统的各项需求。

软件需求分析的建模原则和方法

数据模型：问题的信息域必须被表示和理解

（1）信息内容和关系：信息内容表示了个体数据和控制对象，它们可和其他的数据和控制对象关联。

（2）信息流：信息流表示了数据和控制在系统中流动时变化的方式。

（3）信息结构：信息结构表示了各种数据和控制项的内部组织。

功能模型：软件将完成的功能必须被定义

对进入软件的信息和数据进行变换和处理的模块，它必须至少完成三个常见功能：输入、处理和输出。

行为模型：软件的行为必须被定义

大多数软件对来自外界的事件做出反应，这种刺激／反应特征形成了行为模型的基础。行为模型创建了软件状态的表示，以及导致软件状态变化的事件的表示。

工程化原则

  • 正确理解问题后建模：先准确理解问题，再构建分析模型。
  • 保证需求可回溯：记录每个需求的起源和原因，方便回溯。
  • 开发人机交互原型：制作原型辅助需求分析。
  • 赋予需求优先级：鉴于开发时间紧张，采用迭代增量开发模型，给需求设定优先级。
  • 消除歧义性：因需求常用自然语言描述易产生歧义，利用正式技术评审发现并消除歧义。

软件需求工程

需求工程中的活动可分为两大类，一类属于需求开发，另一类属于需求管理。

软件需求分析过程

  1. 需求获取
    • 对象与难点：获取对象为用户和客户，难点在于用户表达不清需求、各方理解易出现偏差以及用户频繁变更需求。
    • 流程与方法：目的是产出《用户需求说明书》，由需求分析员负责调查分析，相关人员配合提供信息。流程涵盖准备、调查记录、分析、撰写和确认五个步骤，准备工作包括拟定问题表、确定调查方式和计划。调查方式多样，如交谈、观察、问卷等。
    • 需求记录与说明书撰写：调查时建议用表格记录信息，之后分析整理撰写说明书，其与《软件需求规格说明书》不同，前者用自然语言描述较粗略，后者是前者的细化，是软件设计的直接依据。
    • 需求类别：包含功能、性能、环境等多种需求类型，还有其他非功能性需求也需分析。
  2. 软件需求定义
    • 目标与流程：目标是生成《软件需求规格说明书》，由需求分析员定义需求，客户等确认。在《用户需求说明书》基础上，经细化分析、撰写和确认三步完成。
    • 需求分析与综合：针对复杂需求建模，细化软件功能，明确系统元素关系和限制，依据多种需求完善方案，得出目标系统逻辑模型。
    • 需求建模：帮助开发人员理解需求，需构建逻辑模型（关注功能与数据关系）和物理模型（由设备决定功能和数据结构表示形式），有面向对象、结构化等多种建模方法。
    • 编制需求分析文档：包括软件需求规格说明书等多种文档，优质的《软件需求规格说明书》应具备正确、无歧义等多种属性。
  3. 需求确认
    • 流程与内容：开发方和客户共同评审需求文档并书面承诺，确保文档符合要求。评审内容涉及系统目标、文档完整性等多方面，依据正确性、清晰性等指标评判需求优劣。

面型对象需求分析方法

UML概述

一、UML的定义与本质

  1. 定义
    UML（Unified Modeling Language，统一建模语言）是一种标准化的图形化建模语言，用于面向对象分析与设计的可视化表示。
  2. 本质
    • 不是编程语言：不是一种可视化的程序设计语言，而是一种可视化的建模语言。
    • 不是方法或过程：它不是过程，也不是方法，但允许任何一种过程和方法使用它。
    • 不是工具规格：不是工具或知识库的规格说明，而是一种建模语言规格说明，是一种表示的标准。
    • 综合多种方法：融合了Booch、OMT（对象建模技术）、OOSE（面向对象软件工程）等方法的优点。

二、UML的目标

  1. 核心目标
    • 提供表达能力强大且易用的建模语言。
    • 支持跨平台与语言，与实现无关。
    • 促进架构、模式、构件和框架的重用。
    • 集成最佳软件工程实践（如模块化、分层设计）。
  2. 扩展性
    • 通过构造型（Stereotypes）、**标记值（Tagged Values）和约束（Constraints）**扩展核心概念。

三、UML的视图与图

UML通过五类视图和九种图从不同角度描述系统：

1. 用例视图（Use Case View）

  • 作用：描述系统功能需求，从用户角度展示系统行为。
  • 组成图：
    • 用例图（Use Case Diagram）：功能与参与者（Actor）的交互。
    • 活动图（Activity Diagram）（可选）：细化用例的工作流程。

2. 逻辑视图（Logical View）

  • 作用：展示系统的静态结构与动态行为。
  • 组成图：
    • 类图（Class Diagram）：类、接口、关系（继承、关联等）。
    • 对象图（Object Diagram）：某一时刻的对象实例及其链接。
    • 状态图（State Diagram）：对象的状态变化（如订单状态流转）。
    • 活动图（Activity Diagram）：业务逻辑或算法的流程（类似流程图）。

3. 进程视图（Process View）

  • 作用：描述系统并发、同步和通信机制（多线程、分布式场景）。
  • 组成图：
    • 顺序图（Sequence Diagram）：按时间顺序的交互（强调时序）。
    • 协作图（Collaboration Diagram，UML 2.0后称通信图）：对象间的协作关系（强调结构）。

4. 构件视图（Component View）

  • 作用：展示代码构件的物理组织（如库、可执行文件）。
  • 组成图：
    • 构件图（Component Diagram）：构件间的依赖关系（如.dll、.jar文件）。

5. 部署视图（Deployment View）

  • 作用：描述硬件部署及软件到硬件的映射（如服务器、网络拓扑）。
  • 组成图：
    • 部署图（Deployment Diagram）：节点（Node）与构件的部署关系。

四、UML 1.4的九种图详解

图类型 关键用途 适用阶段
用例图 功能需求分析，用户与系统交互 需求分析
类图 静态结构设计（类、接口、关系） 系统设计
对象图 类图的实例化（调试或快照） 详细设计/测试
顺序图 交互时序（如API调用顺序） 动态行为设计
协作图（通信图） 对象协作关系（空间结构） 动态行为设计
状态图 对象生命周期（如订单状态机） 复杂对象建模
活动图 业务流程或算法流程（并行、分支） 需求分析/详细设计
构件图 代码模块化与依赖管理 架构设计/实现
部署图 硬件配置与软件部署 系统部署

五、UML的特点

  1. 可视化：通过图形化符号降低沟通成本。
  2. 通用性：适用于任何编程语言（Java、C++等）和开发过程。
  3. 分层抽象：支持从需求到代码的多层次建模（用例→类→构件→部署）。
  4. 标准化：由OMG（对象管理组）维护，确保工具兼容性。

六、常见应用场景

  • 需求分析：用例图、活动图。
  • 系统设计：类图、顺序图、状态图。
  • 架构设计：构件图、部署图。
  • 调试与维护：对象图、协作图。

测试集和训练集

经验误差与泛化误差

1、就分类问题而言，通常把分类错误的样本数占样本总数的比例称为错误率.

2、对于回归问题，把学习器的实际预测输出与样本的真实标值之间的差异称为误差.

3、如果以训练集样本数据为测量参考，模型在训练集上的误差称为“训练误差”（training error）或者“经验误差”（empirical error）.

4、在测试集上的误差称为“测试误差”（testing error），在新样本上的误差称为“泛化误差”（generalization error）

过拟合和欠拟合

1、在机器学习中太多反映训练样本个性化属性而导致普遍规律受重视不够 引起的，使模型泛化误差大于测试误差的现象称为“过拟合”（overfitting）。 （1）有噪声的数据导致过拟合 （2）训练数据量过少（有限的训练数据）导致过拟合 （3）过于复杂的模型导致过拟合

常用的处理过拟合的一些方法

  • early stopping：当训练精度不再增加的时候停止迭代。
  • 数据集扩增：通过扩充数据集，让训练集中的噪音数据占比越来越小。
  • 正则化：限制模型的复杂度
  • Dropout：
    • 每个训练的batch,随机（依概率p）让一些隐层的节点不工作， 来进行训练（进行参数调整）
    • 测试的时候使用全部网络， 但是权值上乘以概率p（否则预测值会有所扩张）
  • 挑选合适的模型

2、欠拟合是由于模型不能全面反映样本“普遍规律”造成的。训练误差和测试误差、泛化误差都很大。 欠拟合的主要原因是模型不能很好的捕捉数据特征 常用的处理欠拟合的一些方法

  • 添加其他特征项，特征组合、多项式特征等
  • 减少正则化参数
  • 增加模型复杂性

测试样本数据获取方法

方法1：留出法 (Hold-out)

计算学习理论

Jinxiwei published on 0001-01-01 included in 机器学习

计算学习理论（Computational Learning Theory）致力于研究学习的本质和条件，具体回答以下几个问题：

  1. 什么是成功的学习？

    • 成功的学习指的是通过经验或数据，学习算法能够有效地从输入中提取规律，从而做出准确的预测或决策。这意味着，学习算法在面对未知的测试数据时，能够做出与实际情况高度一致的输出。

  2. 在什么样的条件下，成功的学习是可能的？

    • 成功的学习通常在以下条件下更可能实现：
      • 充分的数据量：学习算法需要足够多的训练数据来捕捉数据中的规律。
      • 合适的模型：模型的表达能力必须能够捕捉到数据中的重要特征。
      • 可分性与假设空间：数据是否能被算法有效地分离或拟合，以及算法的假设空间是否能覆盖真实的规律。
      • 噪声与偏差控制：数据中噪声水平较低，且偏差和方差适中。

  3. 在什么条件下，某个特定的学习算法可保证成功运行？

    • 对于一个特定的学习算法，成功运行通常依赖于以下条件：
      • 理论保证：学习算法的设计必须能够在给定条件下保证在大多数情况下能够正确预测，如VC维（Vapnik-Chervonenkis dimension）理论提供的学习能力的上限。
      • 假设空间与数据分布的匹配：如果算法的假设空间与数据的真实分布非常匹配，且假设空间复杂度适当（不太复杂也不太简单），则该算法可以保证成功。
      • 有效的正则化：避免过拟合和欠拟合，能够使算法在不同的训练集和测试集上表现稳定。
      • 充足的训练集：在训练集上，学习算法必须能够找到一个合适的规律，并且能够推广到未知的测试集上。

标准机器学习基本框架

  1. 未知的目标函数 ( c: X \rightarrow Y )

    • 机器学习的目标是学习一个未知的目标函数 ( c )，它表示输入 ( X ) 和输出 ( Y ) 之间的关系。

  2. 训练集

    • 我们通过训练集来进行学习，训练集由一组输入输出对 ((x^{(1)}, y^{(1)}), \dots, (x^{(n)}, y^{(n)})) 组成。

  3. 假设函数集合 ( H )

    • 假设函数集合 ( H ) 包含了多个候选函数 ( h_1, h_2, \dots, h_n )，这些函数是模型用来拟合数据的潜在选项。

  4. 机器学习算法 ( A )

    • 机器学习算法 ( A ) 从假设函数集合 ( H ) 中选择一个最优假设函数 ( g \approx c )，即尽可能接近未知的目标函数 ( c )。
